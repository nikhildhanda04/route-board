Four decisions that set the shape

Locked in before any code

Each of these is the cheap option that still works. Every one has a documented upgrade path if a school outgrows it.

Boarding capture
Driver taps names on a roster
No RFID cards, no readers, no hardware to lose or replace. A pilot can start the week a school says yes. Add scanning only when a school disputes a tap or a bus passes ~40 students.
Parent channel
WhatsApp Business API
Parents install nothing. Messages land where they already look, and arrive on phones that would never keep a school app updated.
Tenancy
Multi-tenant from day one
A school_id on every row and a row-level security policy that enforces it. Adding this after the first three schools is a rewrite, not a migration.
Driver surface
A webapp, not a native app
The driver gets a link and adds it to their home screen. No app store, no review cycle, no support call every time a driver changes phone. Taps are queued locally, so they survive dead zones either way.
Stack
Next.js · Neon Postgres
One repo, one deploy, one npm run dev. Drizzle for schema and migrations, Vercel for hosting and cron. Nothing to keep running at 3am.
Messaging vendor
Meta Cloud API, direct
API access is free and you pay Meta's rate with no reseller markup. A BSP sells an inbox and a flow builder — both of which you are already building.
Architecture

One app, three surfaces, no API server

Everything above the database is one Next.js project on one deploy. Row-level security does authorization in the database, Realtime pushes bus positions straight to the map, and a single edge function sends messages. A Node backend in the middle would add a deploy to maintain and buy nothing.

Why not a native driver app. Native buys exactly one thing: GPS that survives a locked screen. It costs an app-store pipeline and the permanent burden of getting drivers to install and update software. The boarding taps — the part a child's safety depends on — are queued locally and survive anything either way. Build native when a school complains that tracking drops, funded by their money.

Data model

Twelve tables, one of them load-bearing

Everything a parent, a principal or an auditor ever asks is a query over trip_events. There is no separate attendance table to drift out of sync with it.

TableHolds
schoolsThe tenant. Name, timezone, WhatsApp sender identity.
usersStaff accounts — admin, driver or attendant.
studentsName, class, photo, active flag.
guardiansPhone numbers to notify, with a per-guardian opt-out.
busesPlate and capacity.
routesA named pickup or drop run.
stopsLocation, sequence and scheduled time along a route.
route_studentsWhich child boards at which stop on which route.
tripsOne route, bus and driver on one date. Scheduled → running → done.
trip_eventsAppend-only: boarded, alighted, absent. The source of truth.
bus_locationsGPS pings while a trip runs. Pruned after 7 days.
outboxQueued parent messages with status, attempts and last error.
A client-generated ID on every tap. The driver app stamps each event with a UUID before it ever reaches the network. A unique constraint on that column means replaying the offline queue can never send a parent the same message twice.
One security policy, written once. An app_school_id() function in Postgres, reused verbatim across all eleven tenant tables. Every table carries its own school_id even where a join could reach it — one identical policy beats six different join-based ones.
History is append-only, and says so out loud. A trigger rejects any UPDATE or DELETE on trip_events; corrections are recorded as new events. The first attempt used a rule that silently discarded the write and returned success — precisely the kind of thing you discover during an incident.
Messages go through an outbox, not a direct call. The driver may be in a dead zone when the tap happens, and a direct API call has no retry. The outbox makes delivery durable — and gives you a log to point at when a parent says they never got a message.

Build order

Six phases to a pilot

Phases 1 and 2 run in parallel once the schema lands. Roughly 5–6 weeks for one developer; 3–4 for two.

00
Schema, security, seed data — built
Twelve tables, RLS forced on all eleven tenant tables, an append-only trigger on the event log, and two seeded schools so isolation is testable rather than assumed — with nine assertions that prove it, run as the restricted role because a superuser would pass them all for the wrong reason.
done
01
Admin web — auth, students, CSV import, route planner
CSV import is the make-or-break onboarding feature; no school hand-types 800 students. The route planner is a map you click to drop stops, a draggable list to order them, and a picker to assign children to each.
1.5–2 weeks
02
Driver PWA — roster, offline queue, GPS
Four screens, same codebase as the admin, served at /drive with its own mobile layout. A web manifest makes it installable to the home screen — no store, no review, no install support calls.
1 week
03
Outbox and WhatsApp delivery
A database trigger queues one message per guardian; Vercel Cron drains the queue every minute, claiming rows with for update skip locked so overlapping runs cannot double-send. Template approval runs in the background from day one.
4–5 days
04
Live tracking link
A signed token in the message opens a public page with a live bus marker, fed by a server-sent-events route — no parent login, no parent app, no websocket server. This is also the demo that sells the product.
3–4 days
05
School dashboard and exceptions
All buses on one map, plus the screen a principal actually opens: who didn't board, which trips started late, which bus has been stopped too long.
1 week
Unit economics — 5,000 bus students

Scope held back on purpose

Not in v1 — and the signal to add it

None of these are forgotten. Each is waiting on a specific trigger, so the decision to build it comes from a customer rather than from a quiet afternoon.

Left outBuild it when
Native driver appSchools report the live map going stale because drivers background the tab. The boarding record is never affected, so this is a comfort complaint — wait until it is a paying one.
Parent mobile appParents ask for something a WhatsApp message and a map link can't do — leave requests, two-way chat, multiple children in one view.
RFID / NFC scanningA school disputes a manual tap, or a bus carries more students than a driver can reliably tap through.
Automatic route optimizationSchools complain about hand-ordering stops. Then a routing API, not a solver you wrote.
Driver safety reportingA school asks about speeding or harsh braking. The GPS history is already sitting there.
In-app billingAfter the third paying school. Invoice by hand until then.
Multi-language templatesThe first school whose parents don't read English signs.
